# OA 审批语义设计 v1

> 适用：请假审批（P2 试金石流程）· 决策日期 2026-10-30
> 原则：**先定语义，再写代码**。下面每一条都会直接落到 BPMN 节点或表字段上，改动成本高。

## 1. 业务状态机

```
              ┌──────── 提交 ────────┐
   草稿(0) ───┤                      ├──> 审批中(1)
              └──── 删除(物理)        │         │
                                        │         ├── 全部通过 ──> 已通过(2)
                                        │         ├── 任一节点驳回 ──> 回到(1) 等待修改
                                        │         └── 发起人撤回 ──> 已撤销(4)
                                        │
                                    驳回后修改再提交 ──> 仍为(1)，同一流程实例
```

- `0 草稿`：已保存未提交，可编辑可删除，**不产生流程实例**
- `1 审批中`：已产生流程实例，业务表 `status` 由流程事件回写
- `2 已通过`：流程实例正常结束
- `3 已驳回`：**不采用**。驳回不终止流程，只把任务退回发起人，状态仍为 1（见 §3）
- `4 已撤销`：发起人主动终止，流程实例被删除

> 为什么没有「已驳回」终态：驳回是中间态不是终态。给它一个终态会逼出「驳回了还能不能改」的一系列歧义，而实际业务里 90% 的驳回都会改完再提交。

## 2. 审批链路由（按天数）

| 请假时长 | 审批链 |
|---|---|
| ≤ 1 天 | 部门负责人 |
| 1 < 天数 ≤ 3 | 部门负责人 → 人事备案 |
| > 3 天 | 部门负责人 → 人事备案 → 总经理 |

**边界取值**：`days` 以 0.5 天为最小粒度；`≤1` 含 1.0。

**路由位置**：BPMN 排他网关条件表达式判断，**不在代码里 if-else**。这样改规则只改 BPMN，不用发版。

## 3. 驳回语义（最关键的一条）

采用**同实例退回**，不是"驳回另起一单"。

- 驳回动作 = 把执行流从当前审批节点 `changeActivityState` 移回 `submitTask`（发起人修改节点）
- 流程实例、单号、历史记录**全部保留**
- 张三重新提交 = 完成 `submitTask` 任务，流程继续往下走
- 变量（尤其是 `days`）以**最新一次提交为准**，因此「5 天改 2 天」会走新的路由分支 —— 符合直觉
- 审批历史会看到同一节点出现两次，这是正确的审计轨迹，不清理

**为什么不终止实例再新建**：那样单号会变、历史断裂，用户在「我发起的」里看到两条互不相关的记录，体验很差。

## 4. 撤回语义

- 仅允许 `status=1` 且流程未结束时撤回
- 撤回 = `deleteProcessInstance` + 业务状态置 `4`
- 撤回后不可恢复，需重新发起（新单号）
- v1 不校验"当前节点是否已被审批"——撤回即终止，符合多数 OA 的宽松策略

## 5. 审批人解析

| 节点 | 解析规则 | 兜底 |
|---|---|---|
| 部门负责人 | 从 `applyDeptId` 开始**逐级向上**找 `sys_dept.leader` 非空的部门，用 `nick_name` 反查 `sys_user.user_id` | 查不到则指派 `admin`（id=1） |
| 人事备案 | 按角色 key `hr` 取该角色下第一个在职用户 | 查不到则指派 `admin` |
| 总经理 | 按角色 key `gm` 取第一个在职用户 | 查不到则指派 `admin` |

解析逻辑封装在 Spring Bean `oaAssigneeResolver` 中，BPMN 里用 `${oaAssigneeResolver.deptLeader(applyDeptId)}` 调用，**流程定义里不含 Java 类名**。

> 现状：库里只有 `admin`/`common` 两个角色，`hr`、`gm` 角色不存在，因此实际都会兜底到 admin。要演示真实三级审批，需执行 `sql/oa/02_oa_demo_data.sql` 补角色和用户。

## 6. BPMN 结构

```
[start] ─> (提交申请*) ─> (部门负责人审批) ─> <gw1: days<=1?>
                                              ├─ 是 ──────────────────────────> [end]
                                              └─ 否 ─> (人事备案) ─> <gw2: days>3?>
                                                                     ├─ 是 ─> (总经理审批) ─> [end]
                                                                     └─ 否 ─────────────────> [end]
```

`*` 提交申请节点 `assignee=${applyUserId}`，发起后由系统自动完成；驳回时执行流回到这里，变为发起人的待办。

## 7. 接口约定

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/oa/leave/list` | 分页查询（含数据权限） |
| GET | `/oa/leave/{id}` | 详情 |
| POST | `/oa/leave` | 新增（草稿） |
| PUT | `/oa/leave` | 修改（仅草稿/被驳回后） |
| DELETE | `/oa/leave/{ids}` | 删除（仅草稿） |
| POST | `/oa/leave/submit/{id}` | 提交审批，启动流程 |
| POST | `/oa/leave/approve` | 同意，body `{taskId, comment}` |
| POST | `/oa/leave/reject` | 驳回，body `{taskId, comment}` |
| POST | `/oa/leave/revoke/{id}` | 撤回 |
| GET | `/oa/task/todo` | 我的待办 |
| GET | `/oa/task/done` | 我的已办 |
| GET | `/oa/leave/trace/{id}` | 流程跟踪（节点 + 审批记录） |

## 8. v1 明确不做

- 会签/或签（多实例任务）：留到 P3，用 `multiInstanceLoopCharacteristics`
- 加签/转办/委托：需要改运行时任务图，P3 再做
- 流程定义在线设计：P4 接 bpmn-js
- 超时自动提醒：需要开启异步执行器 + 定时边界事件，P3
- 动态业务表单：P4

## 9. 事务边界

- 启动流程与回写 `process_instance_id` 在**同一事务**，失败一起回滚
- 流程结束回调业务表状态：v1 直接在一次审批调用里同步完成（`taskService.complete` 后判断实例是否结束）
- 后续如果需要异步回调，再引入事件监听器，届时需处理重复回调幂等
